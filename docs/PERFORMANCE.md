# 공고 목록 쿼리 성능: 인덱스 측정 (2026-11-24, 로컬)

> **측정 조건을 먼저 읽을 것**
> - 데이터는 **합성 데이터**(스크립트로 생성)이고 실제 서비스 규모가 아니다. 별도 스키마 `daonil_perf`에서 측정했고 서비스 DB는 건드리지 않았다.
> - 로컬 MySQL 8.4, 공고 5,000건 / 30,000건(접수 중 약 72%), 지원 건수는 공고의 1.5배(일부 공고에 쏠림).
> - 측정값은 **MySQL 서버 안의 실행 시간**(`EXPLAIN ANALYZE`의 최상위 actual time, 5회 중 중앙값)이다. 네트워크·JPA·JSON 변환 시간은 포함하지 않는다.
> - 쿼리는 `JobPostingRepository`의 JPQL을 **SQL로 옮긴 근사본**이다(`mysql_code/perf/queries/`). Hibernate가 만드는 SQL과 완전히 같지는 않다.
> - 재현: `mysql_code/perf/01_seed_synthetic.sql` → `02_measure.ps1` → `03_indexes.sql`. 원본 계획·수치는 `mysql_code/perf/results/`.

## 1. 출발점
`job_posting`의 보조 인덱스는 PK, `uk_job_source_ext`, 회사 FK뿐이라 **목록의 필터·정렬 조건에 쓰이는 인덱스가 없다.**

## 2. 결과 (30,000건, 중앙값 ms)
| 쿼리 | 인덱스 없음 | 인덱스 후 | 변화 |
|---|---|---|---|
| q1 기본 목록(접수 중, 최신순 12건) | 107 | 0.14 | **약 750배 빠름** |
| q2 페이징용 전체 건수 | 16.3 | 10.7 | 1.5배 |
| q3 직군+지역 필터 | 44.2 | 0.60 | 약 74배 |
| q4 키워드 검색(흔한 단어) | 105 | 0.74 | 약 140배 (※ 아래 주의) |
| q4b 키워드 검색(**일치 없음**) | 178 | 155 | **거의 안 변함** |
| q5 지원자순 정렬 | 166 | 210 | **오히려 느려짐(약 1.3배)** |
| q5b 지원자순(집계 먼저 하는 재작성) | 157 | 189~354(편차 큼) | 개선 없음 |
| q6 깊은 페이지(OFFSET 10,000) | 132 | 64~78 | 약 2배 |

적용 인덱스(`03_indexes.sql`): `(is_closed, created_at, application_end_date)`, `(main_category, created_at)`.

### 데이터 양에 따른 증가 (인덱스 없음, 5천 → 3만 건 = 6배)
| 쿼리 | 5,000건 | 30,000건 | 배율 |
|---|---|---|---|
| q1 | 23.5 | 104 | 4.4배 |
| q2 | 2.75 | 16.1 | 5.9배 |
| q4 | 24.2 | 106 | 4.4배 |
| q5 | 27.5 | 164 | 6.0배 |

→ 풀스캔이라 데이터 양에 거의 비례해 느려진다.

## 3. 해석
1. **정렬을 인덱스가 대신하면 크게 빨라진다 (q1, q3).** `(is_closed, created_at, …)` 인덱스는 최신순으로 읽다가 12건을 채우면 멈춘다. 전체를 읽고 정렬(filesort)하던 것이 사라진다.
2. **키워드 검색(q4)의 개선은 착시일 수 있다.** "데이터입력"은 흔한 단어라 최신순으로 읽으면 12건이 금방 채워질 뿐이다. 일치하는 공고가 없거나 드문 단어(q4b)는 여전히 전부 읽어야 해서 거의 그대로(178 → 155ms)다. 앞에 `%`가 붙는 `LIKE '%kw%'`는 일반 인덱스를 쓸 수 없다. 해결하려면 FULLTEXT(ngram) 같은 검색 구조 변경이 필요하며 이번에는 측정하지 않았다.
3. **인덱스를 늘렸다고 항상 좋아지지는 않는다.** 처음 시도한 `(is_closed, created_at)` + `(is_closed, application_end_date)` 조합은 목록은 빨라졌지만 **전체 건수는 16ms → 52ms로 느려졌다.** 실행 계획을 보니 옵티마이저가 커버링 인덱스를 고르지 않고 2.7만 행을 테이블에서 하나씩 읽었다. 인덱스를 하나로 합쳐 해결(→ 10.7ms).
4. **지원자순 정렬(q5)은 인덱스로 해결되지 않는다.** 접수 중 공고 2.2만 건을 전부 집계한 뒤 정렬해야 한다. 오히려 인덱스를 추가한 뒤 실행 계획이 임시 테이블을 쓰는 쪽으로 바뀌어 느려졌다. 집계를 먼저 하도록 쿼리를 다시 써도(q5b) 개선이 없었다. 구조적 해결책은 공고에 `applicant_count` 컬럼을 두고 지원 시 갱신하는 방식인데, 일관성 관리가 필요해 구현·측정하지 않았다.
5. **깊은 페이지(q6)는 인덱스로 절반이 되었지만** OFFSET 10,000을 건너뛰는 비용은 남는다. 커서 방식(마지막 id/시각 이후)이 필요하며 측정하지 않았다.

## 4. 한계 (면접에서 먼저 말할 것)
- 합성 데이터라 값의 분포가 현실과 다르다(예: 지역 조합, 키워드 빈도).
- 로컬 PC 측정이다. 서버(Lightsail 2GB)에서의 재확인은 아직 하지 않았다.
- 서버 내부 실행 시간만 쟀다. 화면 응답 시간은 JPA 매핑·N+1(size+2 쿼리) 등이 더해져 다르다.
- 쓰기 비용(인덱스가 늘면 INSERT/UPDATE가 느려짐), 인덱스 용량은 측정하지 않았다.
- 서비스 DB(`daonil`)와 저장소의 `daonil_schema.sql`에는 아직 인덱스를 적용하지 않았다.
