# 동시 사용자 부하 테스트 (2026-11-24, 배포 서버)

> **측정 조건**
> - 대상: AWS Lightsail(시드니, 2GB, Docker Compose: nginx·Spring Boot·MySQL 8.0 한 대), 공고 234건(실제 외부 공고). 합성 데이터 없음.
> - 부하 생성: 이 PC(한국)에서 Node 스크립트(`load/load_test.mjs`). **동시 N명이 응답을 받자마자 다음 요청을 보내는 방식**(폐쇄 루프), 단계당 15초, 워밍업 제외.
> - **네트워크 왕복 지연이 약 228ms**다(같은 방식으로 정적 파일만 내려주는 nginx를 쟀을 때 중앙값). 표의 응답 시간에서 약 228ms는 네트워크다. 단계 간 *차이*를 보면 된다.
> - 조회 전용(인증 없음). 생성·수정 부하는 측정하지 않았다.
> - 서버 자원(CPU·메모리·DB 연결 수)은 1~3절의 측정 때는 수집하지 못했고, 4절에서 같은 시나리오를 다시 걸며 따로 관측했다.
> - 상세 조회는 조회수를 올리므로 측정 중 서버 공고의 `view_count`가 실제로 증가했다(약 1만 4천 회).

## 2. 해석
1. **목록 12건: 동시 약 50명에서 포화.** 처리량이 약 147건/초에서 더 오르지 않고, 50 → 100명에서 p95가 402 → 1,200ms로 뛴다. 늘어난 사용자는 처리되지 않고 대기열만 길어진다. 오류는 없었다(느려질 뿐 실패하지 않음).
2. **목록 100건: 동시 약 25명에서 포화(약 37건/초).** 요청 하나가 쿼리 약 102개(N+1)라 같은 서버가 훨씬 적은 요청만 처리한다. 프론트 AI 챗 화면이 `size=1000`을 쓰므로 해당 화면은 더 취약하다(미측정).
3. **같은 공고에 조회가 몰리면 처리량이 1/3.7로 줄어든다.** 같은 코드 경로에서 공고만 분산시키면 동시 100명에서 392건/초·p50 246ms로 포화가 없다. 같은 공고에 몰릴 때는 106건/초·p50 918ms다. 조회마다 같은 행의 `view_count`를 `UPDATE`하므로 **같은 행의 락 대기가 원인일 가능성이 높다.** 단, 락 대기 자체(예: `performance_schema`)를 관측해 확인하지는 않았다.
   - 대조군도 100개 공고에 분산했을 뿐이라 완전한 "경합 없음"은 아니다.
4. 상세 조회가 목록(쿼리 14개)보다 쿼리가 적은데도 더 일찍 포화하는 것이 3번의 근거 중 하나다.

## 3. 개선: 조회수를 모아서 반영 (적용·재측정 완료)
`ViewCountBuffer`: 조회를 메모리에 모았다가 5초마다 공고별 `UPDATE … + N`을 1회 보낸다. 환경변수 `APP_VIEW_COUNT_BUFFERED`로 켜고 끈다(기본 꺼짐). **같은 서버·같은 부하에서 환경변수만 바꿔 비교했다.**

### 결과 (같은 공고에 조회 집중, 처리량 req/s · p50/p95 ms, 오류 0%)
| 동시 사용자 | 개선 전(1차) | 개선 전(재배포 후 재측정) | **개선 후** |
|---|---|---|---|
| 1 | 4.1 · 242/247 | 4.1 · 246/252 | 4.1 · 242/248 |
| 10 | 41.1 · 238/250 | 40.1 · 241/254 | 41.6 · 235/253 |
| 50 | 102.9 · 471/602 | 88.2 · 554/713 | **208.8** · 232/249 |
| 100 | 106.2 · 918/1020 | 93.6 · 1053/1139 | **412.1** · 235/260 |

- 동시 100명 처리량 **93.6 → 412.1건/초(약 4.4배)**, p50 1,053 → 235ms. 공고를 분산했을 때의 대조군(391.7건/초)과 같은 수준이 되었다. 즉 같은 공고 집중 때의 병목이 사라졌고, 이는 앞의 "같은 행 락 대기" 가설과 일치한다. (락 대기를 직접 관측한 것은 아님)
- 개선 전 두 번의 측정은 약 12% 차이가 난다(106 vs 94). 1회씩 잰 값의 편차이며, 개선 폭(4배 이상)에 비해 작다.
- **정확성 확인**: 같은 공고를 정확히 50번 조회한 뒤 응답의 조회수는 즉시 반영돼 보였고, 5초 뒤 DB 값이 정확히 +50이었다.

### 트레이드오프
- 서버가 비정상 종료되면 최대 5초분의 조회수가 사라질 수 있다(정상 종료 때는 남은 값을 반영). 조회수는 통계에 가까운 값이라 허용했지만, 정확성이 중요해지면 Redis 같은 외부 카운터가 필요하다.
- 조회수 정렬(`sortBy=views`)은 DB 값을 쓰므로 최대 5초 늦게 반영된다.

## 3-3. 개선: 목록의 지원자 수 N+1 제거 (적용·재측정 완료)
공고마다 따로 세던 지원자 수를, 페이지의 공고 id를 모아 `GROUP BY` 쿼리 1번으로 구한다. `size=100` 요청 1건의 SQL이 **102개 → 3개**(로컬 Hibernate 통계로 확인, 회귀 테스트로 고정). 서버에는 재배포했고, 같은 시나리오·같은 방식으로 다시 측정했다. 개선 전 값은 앞의 두 라운드(1·2차)를 쓴다. 이번에는 환경변수 스위치를 두지 않아 같은 서버에서 번갈아 비교하지는 못했다.

| 구간 | 개선 전 처리량 (1차 / 2차) | 개선 후 처리량 | 변화 |
|---|---|---|---|
| 목록 12건, 동시 50명 | 124.7 / 134.7 (평균 129.7) | 162.9 / 171.9 / 173.0 (평균 169.3) | **약 +30%** |
| 목록 12건, 동시 100명 | 135 / 140.8 (평균 137.9) | 189.6 / 199 / 168.6 (평균 185.7) | **약 +35%** (편차 큼) |
| 목록 100건, 동시 25명 | 33.2 / 32.2 | 78.8 (1회) | **약 2.4배**, p50 705~720 → 291ms, p95 967~1328 → 405ms |

응답 시간(목록 12건 동시 100명): p50 665~682 → 418~457ms, p95 1250~1282 → 973~1096ms. 오류는 모든 구간 0%.

### 서버 자원 (개선 후, 구간 표본 12개, 상한 200%)
| 구간 | 백엔드 CPU 평균 | MySQL CPU 평균 | 요청당 CPU (대략) | 개선 전 요청당 CPU |
|---|---|---|---|---|
| 목록12 동시50 (예열 후) | 112% | 53% | 약 10ms | 약 12ms |
| 목록12 동시100 (예열 후) | 105% | 64% | 약 9ms | 약 12ms |
| 목록100 동시25 | 127% | 32% | 약 20ms | 약 45ms |

- **MySQL의 CPU 몫이 줄었고**(목록 100건: 66% → 32%) 요청당 CPU도 줄었다(목록 12건 약 15~25%, 목록 100건 약 55%). 쿼리를 줄인 효과가 서버 자원에서도 보인다.
- **병목은 사라지지 않았다.** 여전히 코어 2개를 평균 159~169% 쓰는 CPU 포화이고, 동시 50명에서 이미 처리량이 거의 한계다(50명 169건/초, 100명 186건/초). 포화가 시작되는 지점은 비슷하지만 **포화 처리량의 상한이 약 30~35% 올랐다.** 병목이 DB에서 백엔드(JVM) 쪽으로 옮겨 갔다.
- 목록 12건의 개선폭(+30%)이 쿼리 감소율(14개 → 3개)보다 작은 것은, 쿼리가 줄어도 JPA 매핑·JSON 직렬화·회사 조인 같은 백엔드 비용이 남기 때문이다.

### 측정의 주의점
- **JVM 예열**: 재빌드 직후 첫 구간(목록12 동시50)은 97.4건/초로 개선 전보다 낮게 나왔고(예열 전), 예열 후 같은 구간은 163~173건/초였다. 같은 이유로 재빌드 직후의 상세 구간(351건/초, 백엔드 CPU 134%)은 이전과 비교하지 않았고, 예열 후 재측정에서 417건/초로 이전 수준(378~416)이었다. 개선 후 수치는 모두 예열 후 값만 썼다.
- 개선 후 동시 100명 2차 반복(168.6건/초)에서 p99 5.2초의 일시적 지연이 한 번 있었다. 원인은 확인하지 못했다.
- 목록 100건은 1회만 측정했고 재빌드 직후라 완전히 예열되지 않았을 수 있다(개선폭은 보수적인 값일 가능성).
- 1회 20초씩 측정, 개선 전은 두 라운드뿐이다. 동시 100명 구간은 반복 간 편차가 약 ±8%.

## 4. 서버 자원 관측 (같은 부하를 다시 걸며 서버에서 기록)
서버 사양: **2 vCPU, 메모리 1.9GB**, 한 대에 nginx·Spring Boot·MySQL 8.0. 서버에서 2~3초 간격으로 `docker stats`, load average, MySQL `Threads_connected/Threads_running`을 기록했다. 도커의 CPU%는 코어 1개 = 100%이므로 **서버 전체 상한은 200%**다. (이 라운드의 PC 측정값: 목록12 동시50 134.7건/초, 동시100 140.8, 목록100 동시25 32.2, 상세(모으기 켜짐) 동시100 377.9. 1~3절의 값과 소폭 다른 것은 1회 측정의 편차.)

| 구간 | 표본 | 백엔드 CPU 평균/최대 | MySQL CPU 평균/최대 | 합계 평균(상한 200%) | load1 최대 | MySQL 연결/실행 최대 | 메모리 최대(백엔드/MySQL) |
|---|---|---|---|---|---|---|---|
| 목록12 동시50 | 12 | 90% / 112% | 71% / 95% | 161% | 4.75 | 11 / 6 | 456 / 115MiB |
| 목록12 동시100 | 12 | 87% / 110% | 76% / 95% | 163% | 7.02 | 11 / 6 | 462 / 116MiB |
| 목록100 동시25 | 13 | 78% / 108% | 66% / 92% | 144% | 8.12 | 11 / 7 | 463 / 118MiB |
| 상세(모으기 켜짐) 동시100 | 11 | 52% / 70% | 33% / 46% | 85% | 7.47 | 11 / 5 | 462 / 118MiB |

### 해석
1. **목록 조회의 병목은 CPU다.** 백엔드와 MySQL이 거의 반반으로 코어 2개를 거의 다 쓴다(평균 합 144~163%, 최대는 상한 근처). load average가 코어 수(2)의 2~4배까지 올랐다. N+1이 DB와 백엔드 양쪽에 일을 만든다.
2. **DB 연결 풀은 병목이 아니었다.** MySQL 연결은 11개(풀 10개 + 측정기), 동시에 실행 중인 쿼리는 최대 6~7개로 풀이 꽉 차지 않았다. 앞의 "연결 풀 대기" 가설은 이 측정에서는 지지되지 않았다. 메모리도 여유가 있다(백엔드 약 460MB, MySQL 약 118MB, 서버 전체 1.9GB).
3. **요청당 CPU 비용(대략)**: 목록 12건 약 12ms, 목록 100건 약 45ms, 상세(모으기 켜짐) 약 2ms (구간 평균 CPU ÷ 처리량, 구간 앞뒤의 한가한 시간이 섞여 있어 실제보다 약간 낮게 잡힘). 같은 서버가 목록 100건은 목록 12건의 1/4, 상세의 1/10 정도밖에 처리하지 못하는 이유다.
4. **조회수 개선 후 412건/초는 서버의 한계가 아니다.** 서버 CPU는 평균 약 85%(상한 200%)였고, 왕복 지연 228ms에서 동시 100명이 낼 수 있는 이론상 최대가 약 438건/초(100 ÷ 0.228)다. 측정값 378~416건/초는 부하 쪽(지연) 한계에 가깝다. 따라서 **"93.6 → 412건/초, 4.4배"는 최소 개선폭**이다. 공고 분산 대조군(392건/초)도 같은 한계에 걸려 있다.

### 이 관측의 한계
- 측정기(`docker stats` 등)가 2~3초마다 돌며 서버 CPU를 조금 쓴다. 표본이 구간당 11~13개뿐이고, 각 구간에 시작·끝의 한가한 몇 초가 섞여 있다(평균은 낮게, 최댓값 중심으로 해석).
- load average는 지연되는 지표라 참고만 한다.
- 락 대기를 직접 관측(`performance_schema` 등)하지는 않았다.

## 5. 한계 (면접에서 먼저 말할 것)
- 서버 자원은 4절에서만 관측했다(구간당 표본 11~13개). 1~3절의 측정과는 별도 라운드다.
- 폐쇄 루프 부하(동시 N명이 쉬지 않고 요청)는 실제 사용자(요청 사이에 생각하는 시간)보다 가혹하다. "동시 사용자 50명"이 실제 접속자 수십 명보다 훨씬 많은 요청량에 해당한다.
- 부하 생성기가 한 대(이 PC)이고 왕복 지연이 크다. 같은 서버 안에서 쏘는 것과 다르다.
- 15초 × 1회 측정이며 반복 측정으로 편차를 구하지 않았다.
- 쓰기 부하(공고 등록·지원)는 아직 없다.
