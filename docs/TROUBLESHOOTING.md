# 배포 중 겪은 문제 사례집 (2026-11-24, 재구축·AWS Lightsail 배포)

> 표시: **[실제 발생]** 작업 중 실제로 일어난 문제 / **[재현]** 원본 코드로 같은 조건을 만들어 확인한 것 / **[측정]** 숫자로 확인한 것
> 모든 항목은 로그·화면·응답으로 확인한 사실만 적었다. 발표 당시 문제와 같다는 증거는 아니며, 같은 유형의 문제를 같은 조건으로 확인한 것이다.

---

## 1. 화면은 뜨는데 공고가 비어 있다 — API 주소가 `localhost`로 고정 **[재현]**
- **증상**: 메인 화면은 정상, "인기 공고" 섹션이 통째로 사라짐.
- **재현**: 환경변수화 이전 커밋(`e92a486`)의 프론트를 그대로 빌드해 백엔드가 없는 환경에서 실행.
- **증거**: 브라우저 콘솔 `인기 공고 데이터 조회 실패: AxiosError: Network Error`, 네트워크 `GET http://localhost:8080/api/jobs?size=100&page=0` → `net::ERR_CONNECTION_REFUSED`.
- **원인**: 코드에 `http://localhost:8080` 고정. 서버에 올리면 사용자 브라우저가 **자기 PC의 8080**을 호출.
- **해결**: API 주소를 `VITE_API_URL`로 분리(`frontend/src/config.js`). 빌드한 번들에 `localhost`가 남지 않는 것을 검사.
- **진단 요령**: 개발자도구 Network 탭에서 요청 주소가 서버 주소인지 본다.

## 2. 개발에서만 되던 상대 경로 호출 약 30곳 **[실제 발생·발견]**
- **발견**: `fetch('/members/login')`, `axios.get('/api/alarms')` 처럼 상대 경로 호출이 여러 파일에 흩어져 있음. 개발 서버(Vite) 프록시 덕분에 개발에서만 동작.
- **영향**: 프론트와 API 주소가 다르면 요청이 프론트 서버로 가서 실패.
- **해결**: 진입점 `setupApi.js`에서 `VITE_API_URL`이 지정된 경우 axios 기본 주소와 상대 경로 fetch에 주소를 한 번에 적용. 브라우저에서 `fetch('/api/jobs')`가 `http://localhost:8080/api/jobs`로 나가는 것을 확인.

## 3. Linux 서버에서만 프론트 빌드 실패 — 파일 이름 대소문자 **[실제 발생]**
- **증상**: `docker compose build frontend`가 `npm run build` 단계에서 실패(`exit code: 1`).
- **원인**: import 경로의 대소문자가 실제 파일과 달랐다(2곳).
  - `CompanyJobPostManage.jsx`: `...CompanyJobPostManageContent` ↔ 실제 `CompanyJobpostManageContent.jsx`
  - `CompanyMypage.jsx`: `components/Company/` ↔ 실제 `components/company/`
- **왜 숨어 있었나**: Windows는 파일 이름 대소문자를 구분하지 않아 개발 환경에서는 정상.
- **해결·검증**: 경로 수정. 프론트 소스 83개 파일의 import를 Git이 기록한 실제 파일 이름과 대소문자까지 비교해 불일치 2건 → 0건.
- **교훈**: 로컬이 Windows여도 Linux 컨테이너 빌드를 CI에서 돌려야 이런 문제를 먼저 잡는다.

## 4. `package-lock.json`이 `package.json`과 어긋남 **[실제 발생]**
- **증상**: `npm ci`가 `package.json and package-lock.json are not in sync`로 실패(`@emnapi/*` 항목 누락).
- **대응**: Dockerfile은 `npm install` 사용. 잠금 파일 자체는 별도 정리 대상.

## 5. 예시 파일에 변수를 추가했는데 서버 `.env`에는 없어 기능이 동작하지 않음 **[실제 발생]**
- **증상**: 외부 공고 동기화를 켰는데 서버 DB가 비어 있음(API `totalElements=0`), 백엔드 로그에 동기화 관련 줄이 없음.
- **진단**: 컨테이너 안의 값을 직접 확인 — `KEAD_SYNC_RUN_ON_STARTUP`이 `false`, 인증키는 정상(97자). `.env`에는 해당 줄이 없었다.
- **원인**: `.env`는 `.env.example`을 **복사해 만든 파일**이라, 예시에 변수를 나중에 추가해도 이미 만든 `.env`에는 자동 반영되지 않는다. 없는 변수는 `docker-compose.yml`의 기본값(`false`)으로 대체됨.
- **해결**: `.env`에 줄 추가 후 `docker compose up -d`(컨테이너를 다시 만들어 반영).
- **교훈**: ① `.env` 수정은 `restart`가 아니라 **컨테이너 재생성**이 필요하다. ② 설정이 반영됐는지는 **컨테이너 안에서 `printenv`로 확인**한다.

## 6. 브라우저 기반 SSH 연결 실패 **[실제 발생]**
- **증상**: Lightsail 콘솔의 SSH 창에서 "연결할 수 없음".
- **진단**: 서버 밖에서 포트 확인 — SSH 22, 웹 80, API 8080 모두 연결됨, HTTP 200. 서버는 정상이고 브라우저 SSH 클라이언트만 실패.
- **대응**: 새로고침·다른 브라우저로 재시도 후 연결됨. 대안으로 PC의 SSH 클라이언트와 키 파일 방식 준비.
- **교훈**: "서버가 죽었다"와 "접속 도구가 실패했다"를 포트·HTTP 응답으로 먼저 구분한다.

## 7. 서버 지역이 의도(서울)와 달리 시드니 **[실제 발생]**
- **발견**: 콘솔 주소의 `ap-southeast-2`로 확인(서울은 `ap-northeast-2`).
- **영향**: 한국에서의 응답 지연(측정: 웹 약 0.6초, API 약 0.5초), 시드니 플랜의 낮은 데이터 전송 한도, 공공 API 접속 영향 가능성.
- **교훈**: 리소스를 만들 때 지역 선택을 먼저 확인한다.

## 8. 동기화 중 실제 실행에서 발견한 버그 — BCrypt 72바이트 한도 **[실제 발생]**
- **증상**: 첫 실행에서 정제 238건이 전부 실패(`password cannot be more than 72 bytes`).
- **원인**: 시스템 계정의 무작위 비밀번호가 73자였다. **모의 인코더를 쓴 단위 테스트는 통과**해서 잡지 못했고, 실제 DB 실행에서 드러남.
- **해결**: 64자로 줄이고 실제 `BCryptPasswordEncoder`로 검증하는 테스트 추가. 정제 서비스는 설계대로 실패를 건별로 기록하고 재실행 때 재시도.

## 9. 목록 API의 N+1 — 공고 수만큼 쿼리가 늘어난다 **[측정]**
- **측정**(로컬 MySQL, 공고 235건, 요청당 SQL `select` 수와 응답 시간):

| 요청 size | 응답 건수 | 응답 시간 | select 수 |
|---|---|---|---|
| 1 | 1 | 35ms | 3 |
| 12 | 12 | 71ms | 14 |
| 50 | 50 | 194ms | 52 |
| 100 | 100 | 324ms | 102 |
| 235 | 235 | 601ms | 237 |

- **해석**: select 수가 항상 `size + 2`. 공고 목록 1회, 페이지 전체 건수 1회, 그리고 **공고마다 지원자 수를 조회하는 쿼리**(`countByJobPosting_JobPostingId`)가 건수만큼 실행된다(N+1).
- **영향**: AI 챗 화면이 `size=1000`으로 공고를 가져오므로 요청 한 번에 약 1,000개의 쿼리가 나갈 수 있다. DB가 같은 서버가 아니라 네트워크 건너편(RDS 등)이면 건당 지연이 곱해져 더 느려진다.
- **개선안**: 현재 페이지 공고 ID 목록으로 지원자 수를 `GROUP BY` 한 번에 집계(쿼리 `size+2` → 3개). 아직 적용하지 않았다.
